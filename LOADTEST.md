# Нагрузочное тестирование (AC-13, §8.1)

**Цель ТЗ:** ~2000 одновременных пользователей; отклик API (кроме LLM) — десятки–сотни мс (NFR-1.6).

Инструмент: [autocannon](https://github.com/mcollina/autocannon). Скрипт: `apps/backend/scripts/loadtest.mjs`.
Запуск: `node scripts/loadtest.mjs [connections] [duration]` (сервер должен быть поднят).

## Что тестировалось

Не-LLM **read-path** — именно к нему относится цель NFR-1.6. LLM-эндпоинты (сократический
диалог, генерация) НЕ нагружались намеренно: их пропускная способность ограничена
моделью и регулируется очередью BullMQ + семафором параллелизма (NFR-1.5, NFR-1.7),
а не приложением. Их нагрузочная проверка — отдельный сценарий против пилотной модели.

## Результаты (одна dev-нода, single Postgres, 250 соединений, 15 с)

| Эндпоинт | Работа | req/s | p50 | p99 | max | ошибки |
|---|---|--:|--:|--:|--:|--:|
| `GET /health` | базовый | **12 681** | 19 ms | 27 ms | 717 ms | 0 |
| `GET /api/me/courses` | auth + запрос | **6 905** | 35 ms | 42 ms | 783 ms | 0 |
| `GET /api/courses/:id/learn` | auth + consent + вложенные include (самый тяжёлый) | **1 996** | 124 ms | 140 ms | 205 ms | 0 |

Высокая конкуренция — **800 соединений** на `/learn`: 1 978 req/s, p50 399 ms, p99 609 ms,
**0 ошибок, 0 таймаутов**. Пропускная способность стабильна, задержка растёт линейно с числом
соединений (закон Литтла), деградация плавная — отказов нет.

## Вывод

- Все задержки в пределах NFR-1.6 («десятки–сотни мс»), **ноль ошибок** на ~350k запросов.
- Даже самый тяжёлый эндпоинт держит ~2000 req/s на одной ноде. 2000 одновременных
  пользователей при реалистичном темпе (запрос раз в несколько секунд) дают нагрузку
  существенно ниже измеренной пропускной способности — **запас кратный**.

## Для полноценной приёмки AC-13 на staging (рекомендация)

Текущий прогон — характеризация на одной dev-ноде, а не распределённый тест 2000 реальных
пользователей. Для формальной приёмки:

1. **Прод-сборка** (`node dist/server.js`, не `tsx`), несколько инстансов за балансировщиком
   (бэкенд stateless — NFR-1.2), воркер генерации отдельным процессом.
2. **PgBouncer** (пул соединений к БД под пик, NFR-1.3).
3. **Распределённые генераторы нагрузки** (k6 Cloud / несколько машин), сценарий из смеси
   реальных пользовательских путей (вход → лекция → тест), рост нагрузки ступенями до 2000.
4. Отдельно — **сценарий чата** против пилотной модели с проверкой очереди и честного
   UI-статуса ожидания при достижении лимитов провайдера (NFR-1.5).
